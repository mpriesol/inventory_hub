# Unified operational log

Implemented at **Nastavenia → Prevádzkový log** (`/settings/logs`), with the
protected, no-store `GET /logs/events` API. A supplier's latest refresh links to
its supplier/run filter. Reading logs never retries a failed operation.

## Coverage and extension contract

The shared `operation_log.emit` / `operation_log.context` interface records:

- Incoming Hub API requests: matched route template, method, HTTP status, elapsed
  time and server-generated request ID. The response exposes `X-Request-ID`.
  Health checks, data downloads and log reads are excluded. Unmatched/rejected
  pre-routing requests use `/unmatched`, never the raw request path.
- Supplier availability worker passes: supplier, feed run ID, start/completion or
  failure. Sloger can have several passes in one durable run; a completed pass
  is not a claim that the whole run or shop publication completed.
- Husky feed download outcomes and B2B HTTP calls: login/listing phase, page,
  HTTP status, redirects, duration, fixed error code. Page validation records
  missing/mismatched pager markers, observed numeric page, invalid row count,
  missing next page and the page limit. HTTP 200 does not prove valid content.

This is an initial integration of one common logger, not comprehensive outgoing
HTTP coverage for every adapter. Add other shared API clients and workers to
this same interface incrementally. Use fixed operation/target codes and context
IDs, never raw URLs or free-form exception messages. A future multi-host setup
can ship this schema to a central collector (for example Loki with retention and
access controls); the current single-host deployment needs no additional stack.

## Retention, privacy and concurrency

`INVENTORY_DATA_ROOT/logs/operations.jsonl` has three rotated archives. Each file
is capped at 5,000,000 bytes: **20 MB total**, plus an empty lock file. Oldest
records are overwritten by size, not by a promised number of days. API reads are
bounded by those same limits. Independent processes/threads coordinate writes,
rotation and reads using a filesystem lock; files are reopened under the lock.
This assumes the existing shared local data mount, not independent replica disks.
Logging failures do not fail an inventory operation. Unreadable history returns
an explicit 503; log absence alone never proves that an operation did not occur.

Only allowlisted scalar metadata is accepted, on both write and read. No bodies,
headers, cookies, credentials, source HTML, customer identifiers, raw paths or
URL queries are recorded. Request IDs are generated by the server. Symlink log
files are rejected. JSONL files are outside the public document allowlist.
The log API requires the existing operator session/token and returns no-store.
General role-based log permissions remain outside this change.

The existing technical `inventory_hub.log` separately retains its 5 MB × 4 file
rotation. The actual deployment overlay and reference Compose also bound the
API container's Docker `json-file` stdout/stderr log to **10 MB × 3 files**.
The deployment recreates the API container, applying that limit. This does not
purge documents, database history or logs belonging to other containers.

Operational events are disposable diagnostics. Immutable movements, FIFO,
request recovery and business audits remain in their existing durable stores;
rotation must never remove them.

## Query and UI behavior

Filters: component, supplier, level, run ID, request ID and inclusive UTC
`since`/`until` timestamps. The UI accepts dates in the operator's local time.
`limit` is 1–200 (default 100); records are newest first. `before` is the returned
opaque event ID. New writes do not shift a cursor page. If rotation removed the
cursor, the API returns `operation_log_cursor_expired` (409), and **Najnovšie**
starts again. Invalid ranges/filters are rejected without echoing input values.
Read failures clear the table; access changes abort requests and clear retained
events. No polling, automatic retries or external API calls occur when browsing.

## Deployment, verification and rollback

No DB migration, credential change or extra dependency. Deploy through the
existing workflow. Reverting the implementation is compatible with existing data;
it leaves only bounded diagnostic files. Keep Docker rotation when rolling back.

Synthetic tests exercise rotation, concurrent writers, stable/expired cursors,
filtering, context propagation, secret exclusion, protected route handling,
failed requests, Husky pager evidence, access changes and help controls. Existing
Husky DB tests remain required in CI. Synthetic tests do not prove a live Husky
refresh; verify a new run and its stored catalog results after deployment.
